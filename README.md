# paperclip-telegram-bridge

Сервис-мост между Paperclip и Telegram. Версия 2 зеркалирует беседы Agent Chat Paperclip (беседы пользователя с агентами во всех его компаниях) в темы одной приватной супергруппы Telegram: ответы агента приходят в тему, текст из темы уходит в беседу как сообщение пользователя. Архитектура — [ADR-0010](docs/adr/0010-v2-forum-bridge.md).

Что важно знать сразу:

- Bridge делает **только исходящие соединения**: к Paperclip (напрямую, без proxy) и к Telegram (только через proxy из `TELEGRAM_PROXY_URL`, например Xray). Входящих портов и webhook нет, Paperclip в интернет не публикуется.
- Без `TELEGRAM_PROXY_URL` процесс не стартует; прямого пути к Telegram в коде нет (`src/telegram/http.rs`, ADR-0005).
- Состояние (связь «тема ↔ беседа», курсоры комментариев, offset Telegram, очереди в обе стороны) хранится в SQLite в каталоге `/state`.
- Сообщение пользователя сначала записывается в очередь и только потом отправляется в Paperclip с детерминированным `clientRequestId`, поэтому оно не теряется при рестарте и не дублируется. Ответ агента после краша может прийти в Telegram повторно (принятый компромисс, ADR-0004).
- Лицензия: Apache-2.0.

## Быстрый старт

Образ в реестры не публикуется: его собирает пользователь. Каталог `deploy/` содержит только пример.

### Что нужно подготовить

1. Бот в Telegram: создать у BotFather, сохранить токен. Для бота не должен быть установлен webhook (иначе `getUpdates` вернёт конфликт, см. [RUNBOOK](docs/RUNBOOK.md)).
2. Приватная супергруппа с включёнными темами (Topics). Бот — администратор с правом «Управление темами» (`can_manage_topics`). Её id (`-100…`) — это `TELEGRAM_CHAT_ID`.
3. Свой Telegram `user_id` (и, при желании, других участников) для `TELEGRAM_ALLOWED_USER_IDS`.
4. Board API key Paperclip того пользователя, чьи беседы зеркалируются (`pcp_board_…`, бессрочный, ADR-0002). Один ключ действует во всех компаниях пользователя. В Paperclip должен быть включён Agent Chat.
5. Рабочий proxy до Telegram (`socks5h://…`, `socks5://…`, `http://…` или `https://…`), доступный из сети контейнера.

### Настройка супергруппы

1. В Telegram создать группу, затем **Настройки группы → Тип группы**: сделать приватной и включить **Темы** (Topics). Группа станет супергруппой с форумом.
2. Добавить бота в группу и назначить администратором с правом **«Управление темами»** (`can_manage_topics`). Без этого права bridge не сможет создавать и открывать темы.
3. Узнать `chat_id`: у супергруппы он отрицательный и начинается с `-100` (например `-1001234567890`). Он виден в ссылке Telegram Web (`#-100…`) или в `chat.id` любого апдейта группы. Значение без `-` или положительное bridge отклонит при старте.
4. Узнать свой Telegram `user_id` (число) и записать в `TELEGRAM_ALLOWED_USER_IDS`. Участников можно перечислить через запятую.
5. Проверить конфигурацию: `docker compose run --rm bridge check-config`. Сама супергруппа проверяется при старте `run`: форум, права бота. Если что-то не так, в логе ERROR с причиной, в healthcheck unhealthy, повтор раз в 5 минут.

Темы создаются автоматически, вручную создавать их не нужно. Сообщения в General не передаются агентам: бот отвечает подсказкой.

### Несколько компаний

Один контейнер, один бот и одна супергруппа обслуживают **все компании** пользователя сразу: bridge сам находит компании и беседы, список компаний обновляется раз в `PAPERCLIP_DISCOVERY_INTERVAL` (60 с). Новая компания или новая беседа получают тему без рестарта и без правки конфига. Тема называется «`<префикс компании>` · `<имя агента>`».

- **Один ключ на все компании** (обычный случай): board API key пользователя действует во всех его компаниях.

  ```env
  PAPERCLIP_TOKEN_FILE=/run/secrets/paperclip_token
  ```

- **Несколько ключей**, если ваша установка выдаёт ключи на компанию: ключи **одного** пользователя, файлы через запятую. Одну переменную из двух задавать нельзя (`PAPERCLIP_TOKEN_FILE` и `PAPERCLIP_TOKEN_FILES` вместе, а также один файл дважды — ошибка конфигурации).

  ```env
  PAPERCLIP_TOKEN_FILES=/run/secrets/pc_company_a,/run/secrets/pc_company_b
  ```

  В compose каждый файл подключается отдельным секретом. Если компанию видят несколько ключей, используется первый по порядку в списке.

Если Paperclip отвечает 401 (ключ отозван), healthcheck показывает unhealthy. Если опрос бесед компании вернул 403 или 404, эта компания пропускается до следующего обнаружения, остальные работают.

### Что синхронизируется

Источник истины — беседа в Paperclip, тема — её зеркало.

| Где написано | В Paperclip | В Telegram |
|---|---|---|
| Вы пишете в теме | комментарий пользователя, агент просыпается | ваше сообщение; bridge его повторно не присылает |
| Агент отвечает (включая квитанции) | комментарий агента | сообщение бота в теме |
| Служебное сообщение Paperclip (сбой или отмена запуска, системное уведомление) | комментарий | сообщение в теме с пометкой ⚠️ |
| Вы пишете в Paperclip UI | комментарий пользователя | **не пересылается**; ответ агента придёт в тему |

**Не синхронизируется:** правки и удаление сообщений (в обе стороны), вложения, медиа и стикеры, карточки взаимодействий, история беседы до подключения (новая тема начинается с момента обнаружения беседы), переименование агента (тема не переименовывается), создание бесед из Telegram.

### Сборка и запуск

```bash
docker build -t paperclip-telegram-bridge:local .

# файлы секретов: см. «Хранение секретов (rootless Docker)» ниже;
# каталог secrets/ в .gitignore, права и владелец файлов важны

cp .env.example .env            # заполнить плейсхолдеры своими значениями
cp deploy/compose.example.yml compose.yml   # поправить имена внешних сетей

# если Paperclip и Xray слушают loopback хоста: cp deploy/compose.host-network.example.yml compose.yml
docker compose run --rm bridge check-config   # exit 0 и строка "configuration OK"
docker compose up -d
docker compose ps                              # статус healthy появится после start-period (30 с)
```

Секреты читаются **только из файлов** (`PAPERCLIP_TOKEN_FILE`, `TELEGRAM_BOT_TOKEN_FILE`); переменных с самими токенами нет намеренно. Каталог `secrets/` и `.env` уже в `.gitignore`, ответственность за «не закоммитить» на пользователе не лежит. CI (job `gitignore-secrets`) проверяет, что `git check-ignore` возвращает оба пути `secrets/telegram_bot_token` и `secrets/paperclip_token`, и падает, если правило убрать (`scripts/gitignore-check-test.sh`). Не кладите в репозиторий реальные или тестовые токены.

#### Хранение секретов (rootless Docker)

В rootless Docker рекомендуется **строгий вариант** прав:

```sh
install -d -m 0700 secrets
( umask 077; printf '%s' '<telegram bot token>' > secrets/telegram_bot_token )
( umask 077; printf '%s' '<paperclip token>'     > secrets/paperclip_token )
docker run --rm --network none -v "$PWD/secrets:/s" busybox:1.37 \
  sh -c 'chown 65532:65532 /s/telegram_bot_token /s/paperclip_token && chmod 0400 /s/telegram_bot_token /s/paperclip_token'
```

Контейнер в составе bridge запускается с UID 65532. Файлы `0400` собственные этому UID, хост-пользователь их не читает (это дополнительная защита). **Ротация:** удалить файл, записать новый, повторить рецепт.

**Допустимый вариант** (проще, менее строго): `chmod 0644` для файлов в каталоге `0700` хост-пользователя:

```sh
install -d -m 0700 secrets
( umask 077; printf '%s' '<telegram bot token>' > secrets/telegram_bot_token )
( umask 077; printf '%s' '<paperclip token>'     > secrets/paperclip_token )
chmod 0644 secrets/telegram_bot_token secrets/paperclip_token
```

**Не используйте:** `chmod 0400`, `0600`, `0640` для файла, владелец которого хост-пользователь: контейнер с UID 65532 такой файл не прочитает, и bridge не стартует. Проверяет job `rootless-secrets` (`scripts/secrets-rootless-test.sh`): в rootless Docker UID 65532 контейнера соответствует host-UID `subuid_start + 65531`, и матрица прав (строгий вариант, `0400`, `0600`, `0640`, `0644`) сверяется с ожидаемой; при расхождении job падает. Rootful Docker не проверялся.

В `deploy/compose.example.yml` контейнер запускается с `read_only: true`, `user: 65532:65532`, `cap_drop: [ALL]`, `no-new-privileges`, `tmpfs` на `/tmp`, без `ports:`, с именованным томом `bridge-state` на `/state` и `stop_grace_period: 30s`, и подключается только к внешним сетям `paperclip_internal` и `xray_egress` (имена-плейсхолдеры, замените на свои). Сети без маршрута в интернет — дополнительная защита от прямого выхода.

#### Вариант для хоста с Paperclip и Xray на loopback (`network_mode: host`)

Файл `deploy/compose.host-network.example.yml` рассчитан на хост, где Paperclip слушает `http://127.0.0.1:3100`, а Xray отдаёт HTTP proxy на `http://127.0.0.1:10808` (значения в файле — примеры, поправьте под себя). Контейнер работает с `network_mode: host`, `PAPERCLIP_URL` и `TELEGRAM_PROXY_URL` заданы прямо в `environment` (они важнее `.env`), входящих портов нет. Hardening тот же, что в изолированном примере: `read_only`, `65532:65532`, `cap_drop: [ALL]`, `no-new-privileges`, `tmpfs /tmp`, отдельный том `bridge-state`, `stop_grace_period: 30s`. Секреты готовятся так же, как выше. Это отдельный файл, а не override: `network_mode` несовместим с `networks`, поэтому наложить его на первый пример нельзя без `!reset`.

**Компромисс.** При `network_mode: host` у контейнера нет сетевой изоляции: у него есть прямой маршрут в интернет и доступ ко всем loopback-сервисам хоста. Сетевая защита изолированного варианта (сети без маршрута наружу) здесь теряется. Остаётся защита на уровне приложения: клиент Telegram всегда идёт через `TELEGRAM_PROXY_URL` и обходного пути не имеет (при недоступном proxy запросов к Telegram нет вообще), переменные `HTTP(S)_PROXY` не читаются, клиент Paperclip работает без proxy. Ограничение egress на хосте (firewall) вне поставки и не проверялось. Подробнее: [THREAT_MODEL](docs/THREAT_MODEL.md), [RUNBOOK](docs/RUNBOOK.md) §6. В rootless Docker `network_mode: host` видит loopback хоста, если демон запущен с `--detach-netns` (проверено на Docker 29.10.0 в CI); в старых установках это не так.

CI проверяет оба примера: `docker compose config` с сравнением hardening (job `compose-config`) и запуск (`scripts/compose-smoke.sh`, job `docker`). Живой деплой на сервер пользователя не выполнялся.

### Команды бинаря

`bridge [run|check-config|healthcheck|revoke-paperclip-key]` (`src/main.rs`). Бинарь лежит по пути `/usr/local/bin/bridge`, это ENTRYPOINT образа; в образе нет shell.

| Команда | Что делает | Exit |
|---|---|---|
| `run` (по умолчанию) | запускает сервис | 0 штатная остановка, 1 сбой, 2 неверная конфигурация |
| `check-config` | проверяет конфигурацию и собирает HTTP-клиенты без сетевых вызовов | 0 / 2 |
| `healthcheck` | читает heartbeat-файл, без сети (используется `HEALTHCHECK`) | 0 healthy / 1 unhealthy |
| `revoke-paperclip-key` | `POST /api/cli-auth/revoke-current` ключом из `PAPERCLIP_TOKEN_FILE` (читает только эту переменную; при `PAPERCLIP_TOKEN_FILES` задайте её путём к отзываемому ключу) | 0 / 1 / 2 |

Примеры с compose: `docker compose run --rm bridge check-config`, `docker compose exec bridge /usr/local/bin/bridge healthcheck`.

## Конфигурация

Источник правды — `src/config.rs`. Значения по умолчанию ниже взяты оттуда. Длительности: `500ms`, `15s`, `2m`, `1h`, `1d` и суммы вида `1h 30m`; ноль запрещён. Неизвестные переменные игнорируются. Сообщения об ошибках называют переменную и причину, но не значение.

### Обязательные

| Переменная | Описание |
|---|---|
| `PAPERCLIP_URL` | базовый URL Paperclip (`http://` или `https://`; путь-префикс поддерживается) |
| `PAPERCLIP_TOKEN_FILE` | файл с board API key (одна строка; пустой файл или несколько строк — ошибка) |
| `PAPERCLIP_TOKEN_FILES` | вместо `PAPERCLIP_TOKEN_FILE`: несколько файлов ключей **одного** пользователя через запятую. Задавать обе переменные нельзя |
| `TELEGRAM_BOT_TOKEN_FILE` | файл с токеном бота |
| `TELEGRAM_CHAT_ID` | id супергруппы с темами (`-100…`) |
| `TELEGRAM_ALLOWED_USER_IDS` | Telegram `user_id` через запятую: кому разрешено писать агентам |
| `TELEGRAM_PROXY_URL` | proxy для Telegram: схемы `http`, `https`, `socks5`, `socks5h` (рекомендуется `socks5h`: DNS разрешает proxy). Может содержать логин и пароль, в логи и ошибки не попадает |

### Необязательные

| Переменная | По умолчанию | Описание |
|---|---|---|
| `PAPERCLIP_UI_URL` | пусто | базовый URL UI; если задан, в обрезанном длинном ответе есть ссылка `<UI>/<PREFIX>/issues/<ID>` |
| `TELEGRAM_API_BASE_URL` | `https://api.telegram.org` | база Bot API (для тестов) |
| `STATE_PATH` | `/state/bridge.db` | файл SQLite; каталог должен быть доступен на запись (рядом `-wal`, `-shm`) |
| `HEALTH_FILE` | `/state/health.json` | heartbeat-файл |
| `HEALTH_MAX_STALE` | `5m` | сколько может не быть успешного вызова Telegram или Paperclip, прежде чем `healthcheck` вернёт unhealthy |
| `PAPERCLIP_POLL_INTERVAL` | `5s` | опрос списка бесед и «горячих» бесед |
| `PAPERCLIP_DISCOVERY_INTERVAL` | `60s` | обновление списка компаний и имён агентов |
| `PAPERCLIP_SWEEP_INTERVAL` | `60s` | страховочное чтение «холодных» бесед |
| `CONVERSATION_HOT_WINDOW` | `10m` | сколько беседа читается каждый цикл после активности |
| `TELEGRAM_GROUP_MIN_INTERVAL` | `3s` | пауза между вызовами Telegram, меняющими чат (лимит 20 сообщений в минуту на группу) |
| `TELEGRAM_LONG_POLL_TIMEOUT` | `25s` | таймаут long polling, не больше `50s` |
| `PAPERCLIP_REQUEST_TIMEOUT` | `15s` | таймаут запроса к Paperclip |
| `TELEGRAM_REQUEST_TIMEOUT` | `15s` | таймаут запроса к Telegram |
| `CONNECT_TIMEOUT` | `10s` | таймаут соединения (оба клиента) |
| `RETRY_BASE_DELAY` | `1s` | начало экспоненциального backoff с полным jitter |
| `RETRY_MAX_DELAY` | `60s` | потолок backoff; не меньше `RETRY_BASE_DELAY` |
| `RETRY_MAX_ATTEMPTS` | `6` | после стольких отказов Telegram (кроме сетевых) кусок ответа отбрасывается с ERROR; сообщения в Paperclip ретраятся бессрочно |
| `RETRY_NOTIFY_AFTER` | `5` | после какой по счёту неудачной попытки доставки сообщения в Paperclip в тему приходит одно «сообщение в очереди» |
| `MAX_MESSAGE_CHUNKS` | `3` | максимум сообщений Telegram на один ответ агента (до 3500 символов UTF-16 каждое); остальное обрезается с указанием «полностью — в Paperclip» |
| `SHUTDOWN_GRACE` | `10s` | см. «Остановка» |
| `LOG_LEVEL` | `info` | `error`, `warn`, `info`, `debug` (переменная `RUST_LOG` не читается) |
| `LOG_FORMAT` | `json` | `json` или `text`; логи пишутся в stderr |

Переменные v1 `PAPERCLIP_COMPANY_IDS` и `TELEGRAM_USER_ID` отклоняют старт с подсказкой; `PAPERCLIP_RUNS_POLL_INTERVAL`, `PAPERCLIP_GOVERNED_TIMEOUT`, `GOVERNED_*`, `NOTIFY_*` больше не используются — только WARN при старте.

## Как это работает

- Bridge сам находит компании ключа и беседы пользователя с агентами. На каждую беседу создаётся тема «`<префикс компании>` · `<имя агента>`», сразу при обнаружении, без рестарта. Беседа, исчезнувшая из Paperclip, отвязывается от темы.
- В тему приходят ответы агента беседы и квитанции Paperclip («принято»). Служебные сообщения Paperclip (сбой или отмена запуска агента, системные уведомления) приходят с пометкой ⚠️. Сообщения пользователя и комментарии других агентов не пересылаются. История до подключения беседы не пересылается.
- Markdown ответа превращается в разметку Telegram; длинный ответ режется на сообщения не длиннее 3500 единиц UTF-16 (`render/text.rs: CHUNK_LIMIT`, запас под экранирование и теги; лимит Telegram — 4096).
- Текст, написанный в теме, уходит в беседу как сообщение пользователя и будит агента, как сообщение из UI. `/new` уходит как есть и начинает новую сессию агента.
- Сообщения в General, в темы без беседы, медиа и стикеры не передаются: бот отвечает подсказкой. Сообщения из чужих чатов и от пользователей не из `TELEGRAM_ALLOWED_USER_IDS` молча пропускаются.
- Удалённая тема создаётся заново, закрытая — открывается. Если беседа на паузе, бот сообщает об этом в теме.
- При старте бот проверяет супергруппу (форум, права администратора с «Управлением темами»). При ошибке — ERROR в логе и unhealthy, повтор раз в 5 минут, контейнер не уходит в цикл рестартов.

## Переход с v1

v2 — **breaking-релиз** (2.0.0): карточки v1 удалены, `TELEGRAM_CHAT_ID` теперь id супергруппы, а не личного чата.

1. Создать приватную супергруппу и включить темы (см. «Настройка супергруппы»).
2. Добавить бота администратором с правом «Управление темами».
3. Добавить себя в группу; `TELEGRAM_ALLOWED_USER_IDS` = свой `user_id`.
4. `TELEGRAM_CHAT_ID` = id супергруппы (было: id личного чата).
5. **Удалить** `PAPERCLIP_COMPANY_IDS` и `TELEGRAM_USER_ID`: пока они заданы, `bridge` не стартует и пишет подсказку (`check-config` завершится с кодом 2). Остальные переменные v1 (`GOVERNED_*`, `NOTIFY_*`, `PAPERCLIP_RUNS_POLL_INTERVAL`, `PAPERCLIP_GOVERNED_TIMEOUT`) можно удалить по желанию: если заданы, при старте только WARN.
6. Ключ Paperclip и файлы секретов остаются прежними.
7. Volume `/state` остаётся прежним. При первом запуске миграция 2 удалит таблицы карточек v1 (вопросы, подтверждения, governed) и создаст таблицы v2; сохраняется только offset Telegram. Резервную копию перед обновлением сделайте по [docs/BACKUP_RESTORE.md](docs/BACKUP_RESTORE.md): откат на v1 после миграции без восстановления копии невозможен.
8. Убедиться, что в Paperclip включён Agent Chat (беседы видны в UI).
9. `docker compose run --rm bridge check-config`, затем `docker compose up -d`. Для каждой существующей беседы создаётся тема: лимит Telegram 20 сообщений в минуту, 28 бесед — около полутора минут.

Что изменилось для пользователя: карточки v1 (вопросы, подтверждения, governed) в Telegram больше не показываются, решать их нужно в Paperclip; команды `/status`, `/backlog`, `/cancel`, `/help` и уведомления о сбоях run и завершённых задачах удалены (сбои запуска теперь приходят в тему с ⚠️). Подробности: [CHANGELOG](CHANGELOG.md).

## Проверка версии Paperclip

При старте bridge читает `version` из `GET /api/health` и сравнивает её с проверенной версией (константа `TESTED_PAPERCLIP_VERSION` в `src/paperclip/version.rs`, сейчас `2026.1106.0`). Совпадение: обычная запись INFO. Другая версия, отсутствующая или не формата `YYYY.MMDD.N`: WARN с версией сервера и проверенной. **Запуск не блокируется ни в одном случае.** Подробнее: [docs/paperclip-api.md](docs/paperclip-api.md) §3.

## Безопасность

### Включите 2FA в Telegram

Тот, кто получил доступ к вашему аккаунту Telegram (кража сессии, SIM-swap, открытое чужое устройство), пишет агентам через bridge от вашего имени во всех ваших компаниях Paperclip. Поэтому **включите облачный пароль (двухэтапную проверку) в Telegram и периодически проверяйте активные сессии**. PIN в чате не вводится: тот, кто видит чат, видел бы и его. Подробнее: [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md).

Allowlist: обрабатываются только updates `message` из супергруппы `TELEGRAM_CHAT_ID` от пользователей из `TELEGRAM_ALLOWED_USER_IDS`. Остальное молча пропускается (без ответа), в лог пишется не чаще одной записи в 10 секунд (причина и короткий хеш ID, без текста) — `src/core/allowlist.rs`.

Тот, кто может писать в супергруппу от имени разрешённого пользователя, пишет агентам от вашего имени. Держите группу приватной, не добавляйте лишних участников.

### Ключи

Board key даёт **полный доступ пользователя-владельца** и бессрочный (решение пользователя, ADR-0002). Сузить его по правам нельзя. Меры: хранить только в файле секрета, быстро отзывать при подозрении. Процедуры: [docs/RUNBOOK.md](docs/RUNBOOK.md).

## Остановка (`SHUTDOWN_GRACE` и `stop_grace_period`)

При SIGTERM/SIGINT (`src/shutdown.rs`) `src/app.rs` делает два последовательных ожидания по `SHUTDOWN_GRACE`: сначала опрос Telegram, обнаружение бесед, проверки и запись heartbeat, затем очередь в Paperclip (доотправка сообщения, которое уже в работе). В худшем случае это **2 × `SHUTDOWN_GRACE`**, плюс остановка отправщика сообщений и `PRAGMA wal_checkpoint(TRUNCATE)`, которые таймаутом не ограничены.

Правило: **`stop_grace_period` в compose строго больше `2 × SHUTDOWN_GRACE` с запасом.** По умолчанию `SHUTDOWN_GRACE=10s`, поэтому в `deploy/compose.example.yml` стоит `stop_grace_period: 30s`. Меняете `SHUTDOWN_GRACE` — пересчитайте (например, `15s` → не меньше `40s`).

Что будет, если контейнер всё же получил SIGKILL: незавершённое сообщение после рестарта возвращается из `in_flight` в `pending` и отправляется повторно с тем же `clientRequestId`; Paperclip возвращает уже созданный комментарий, второго комментария нет. Наблюдение из CI: при недоступных upstream `docker stop` в smoke-тесте занял 10,17 с при `SHUTDOWN_GRACE=10s` (run 43833870661, шаг 11), то есть почти весь grace; причина не исследована.

## Healthcheck

Сетевых запросов нет. Раз в 15 секунд сервис атомарно пишет `HEALTH_FILE` (`pid`, `started_at`, `written_at`, `last_telegram_ok_at`, `last_paperclip_ok_at`, `last_discovery_ok_at`, `paperclip_auth_ok`, `telegram_group_ok`, `telegram_send_ok`, `agent_chat_ok`, `queue_depth`). `bridge healthcheck` возвращает unhealthy, если файл старше 60 секунд или не читается; Paperclip отклонил ключ (401); в Paperclip выключен Agent Chat; супергруппа не прошла проверку при старте; Telegram отвечает 403 на отправку; либо нет успешного вызова Telegram или Paperclip дольше `HEALTH_MAX_STALE` (до первого успеха отсчёт идёт от старта процесса). `HEALTHCHECK` в Dockerfile: интервал 30 с, таймаут 3 с, start-period 30 с, 3 попытки.

## Известные ограничения v2

- **Бессрочный board key с полным доступом пользователя** — главный остаточный риск; принят пользователем. Ключ не сужается по правам. Его нет в состоянии и backup.
- **Лимит Telegram 20 сообщений в минуту на всю супергруппу.** Длинные ответы нескольких агентов одновременно копятся в очереди (`queue_depth` в healthcheck, WARN при очереди больше 60). Создание тем при первом запуске идёт через ту же очередь: 28 бесед — около полутора минут.
- **Тексты ошибок Telegram для удалённой и закрытой темы не проверены вживую** ([docs/paperclip-api.md](docs/paperclip-api.md) §8); классификатор работает по подстрокам.
- **Пробуждение агента комментарием board-ключа проверено только по коду Paperclip** (ADR-0010 §1.3); живой smoke-тест — на этапе приёмки.
- **Agent Chat в Paperclip — experimental-флаг.** Если его выключат или изменят API бесед, бридж потеряет источник (обнаруживается: сообщение в General, unhealthy).
- Ответ агента может прийти в Telegram повторно, если процесс упал между отправкой и записью в SQLite (ADR-0004). Сообщения в Paperclip не дублируются.
- Передаётся только текст: медиа, правки и удаления сообщений не синхронизируются, история до подключения беседы не переносится. Тема не переименовывается при переименовании агента.
- **Пометка ⚠️ у сообщений о сбое запуска агента зависит от чтения `GET /api/heartbeat-runs/{id}` board-ключом.** Эти сообщения Paperclip публикует от имени агента, и признак — неуспешный запуск. Если board-ключу запуск недоступен или запрос не удался, сообщение придёт в тему **без** ⚠️ (не потеряется). Системные комментарии (`authorType: "system"`) получают ⚠️ в любом случае.
- Содержание переписки проходит через серверы Telegram. В логах содержания нет.
- Нет подкоманды backup: онлайн-копия делается внешним контейнером с `sqlite3` ([docs/BACKUP_RESTORE.md](docs/BACKUP_RESTORE.md)).
