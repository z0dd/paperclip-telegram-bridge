# ADR-0001. Источник pending-вопросов — лента `attention` и карточки задачи

- Статус: принято
- Контекст: [docs/paperclip-api.md](../paperclip-api.md) §4, §5, §10

## Контекст

Bridge должен находить все карточки (interactions), на которые может ответить владелец ключа, и не нагружать Paperclip. Вебхуков нет, Paperclip находится в приватной сети.

## Решение

- Каждые `PAPERCLIP_POLL_INTERVAL` bridge читает первую страницу `GET /api/companies/{companyId}/attention?limit=100&sort=activity` для каждой компании из `PAPERCLIP_COMPANY_IDS`. По курсору он идёт дальше, только если `totalCount` больше; при `400` на курсоре первая страница запрашивается заново.
- Лента уже отфильтрована по адресату, но payload карточек в ней нет, а несколько подтверждений одной задачи она схлопывает. Поэтому для задач с новыми или изменившимися элементами bridge читает `GET /api/issues/{issueId}/interactions` и берёт **все** pending-карточки задачи. Карточки, которых нет в ленте, доставляются, только если у них нет адресата-агента и адресат-пользователь — не другой пользователь.
- Открытые карточки, выпавшие из ленты, перечитываются: так bridge узнаёт, что их решили в другом месте.
- Обход всех задач компании не используется.

## Последствия

- В покое — около 5 запросов в минуту на компанию, независимо от числа задач.
- Элементы `failed_run` ленты используются как источник финальных сбоев run, дополнительно к опросу `heartbeat-runs`.
- Если лента недоступна (например, `403`), fallback не включается: ключ неверный, bridge сообщает об этом.
