# ADR-0003. SQLite (WAL, synchronous=FULL) вместо JSON-файла состояния

- Статус: принято

## Контекст

Обработка одного Telegram update должна атомарно менять offset, черновик формы и очередь ответов. Нужно пережить kill -9, потерю питания и рестарт без потери и дублирования ответов, а также делать онлайн-backup.

## Решение

- SQLite через `rusqlite` (`bundled`), `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`. Файл `STATE_PATH` (по умолчанию `/state/bridge.db`); writable должен быть каталог `/state` (рядом лежат `-wal` и `-shm`).
- Одно соединение живёт в выделенном потоке-актёре; асинхронный код передаёт ему замыкания через канал. Каждый публичный метод `Store` — одна транзакция; `core` не видит rusqlite.
- Схема версионируется через `PRAGMA user_version`. При старте выполняется `PRAGMA integrity_check`: повреждённая БД или схема новее поддерживаемой — отказ старта без автопочинки.
- Восстановление при старте: `outbox.in_flight → pending`, доставки в статусе `sending` отправляются повторно.

## Последствия

- Нужен C-компилятор в builder-образе (он есть в `rust:*-slim`).
- Backup онлайн: `VACUUM INTO` из отдельного контейнера с тем же volume (в runtime-образе нет shell и `sqlite3`). Подкоманды `bridge backup` в v1 нет.
- Restore: остановить bridge, заменить `bridge.db`, удалить `-wal`/`-shm`, запустить. Повторные updates после отката не дублируют ответы (ADR-0004), но карточки после точки backup будут показаны повторно.
