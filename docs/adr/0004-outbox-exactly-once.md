# ADR-0004. Outbox и условное разрешение на сервере — «ответ ровно один раз»

- Статус: принято
- Контекст: [docs/paperclip-api.md](../paperclip-api.md) §7

## Контекст

Idempotency key для ответов в Paperclip нет. Сервер разрешает карточку условным `UPDATE … WHERE status='pending'`: в гонке побеждает один запрос, остальные получают `409`.

## Решение

- Ответ пользователя пишется в таблицу `outbox` в той же транзакции, что и offset породившего update. `outbox.delivery_id UNIQUE`: не больше одного ответа на карточку; повторное нажатие отвечает «Ответ уже отправляется».
- `outbox_worker` отправляет запрос; временные ошибки (таймаут, соединение, `5xx`, `429`, `409` без кода) ретраятся бессрочно с backoff до `RETRY_MAX_DELAY`. После `RETRY_NOTIFY_AFTER` неудач пользователь получает одно сообщение «ответ в очереди».
- `409` с кодом `interaction_*` — reconcile: карточка перечитывается. Если её решил пользователь (не агент) и результат совпадает с отправленным — это наш ответ, ответ сервера просто потерялся. Иначе — «Уже решено в Paperclip, ваш ответ не отправлен».
- `422` возвращает карточку пользователю с текстом сервера (запись outbox удаляется, черновик сохраняется). `403` с audience-кодом закрывает карточку.
- После завершения тело запроса (`body_json`) стирается.

## Последствия

- Падение после HTTP-запроса и до коммита приводит к повтору после рестарта; повтор получает `409` и закрывается через reconcile — двойного ответа нет (crash-тесты `tests/crash.rs`).
- Падение между `sendMessage` и коммитом может показать карточку дважды; ответ при этом не дублируется. Это задокументированный компромисс.
- `userId` владельца ключа bridge узнаёт из ответа на свой первый успешный POST и хранит в `meta`.
