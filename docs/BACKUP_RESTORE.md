# Backup и restore состояния

## Что в состоянии и что нет

Состояние — каталог `/state` (именованный том `bridge-state` в `deploy/compose.example.yml`): `bridge.db` с файлами `bridge.db-wal` и `bridge.db-shm`, а также `health.json` (его восстанавливать не нужно). В `bridge.db`: offset Telegram, карточки и соответствие сообщений, черновики форм, очередь ответов, списки уже показанных сбоев. **Ключа Paperclip и токена бота там нет**; они лежат в файлах секретов, которые вы храните и копируете отдельно по своей политике. Но в базе есть тексты карточек (вопросы агентов): относитесь к копии как к конфиденциальным данным.

## Ограничения инструментов

- Runtime-образ distroless: нет shell, `sqlite3`, `tar`, `cp`. Внутри контейнера bridge ничего из перечисленного выполнить нельзя.
- Подкоманды `bridge backup` в v1 нет (ADR-0003). Online-копия делается **отдельным контейнером с `sqlite3`** над тем же томом; образ с `sqlite3` репозиторий не поставляет, возьмите любой подходящий.
- Команды этого документа в рамках этапа QA **не выполнялись** на реальном томе (нет Docker и развёртывания); они выведены из архитектуры (ADR-0003, раздел 3.3 архитектуры) и поведения SQLite. Перед тем как на них полагаться, проверьте backup и restore на тестовом томе.

Имя тома: `docker volume ls | grep bridge-state` (Compose добавляет префикс проекта). Ниже он обозначен `<project>_bridge-state`.

## Backup

### Вариант A: online, без остановки (рекомендуемый)

`VACUUM INTO` создаёт согласованную копию, не блокируя bridge надолго. Целевого файла не должно существовать.

```bash
mkdir -p backup
docker run --rm --user 65532:65532 \
  -v <project>_bridge-state:/state \
  -v "$PWD/backup":/backup \
  <образ-с-sqlite3> \
  sqlite3 /state/bridge.db "VACUUM INTO '/backup/bridge-$(date +%F).db'"
```

Том монтируется на запись, потому что SQLite в режиме WAL при чтении использует файл `-shm`; монтирование `:ro` может не сработать (не проверено). Каталог `backup` на хосте должен быть доступен на запись пользователю `65532` (или уберите `--user` и поправьте права получившегося файла).

### Вариант B: офлайн, с остановкой

```bash
docker compose stop bridge          # штатная остановка делает wal_checkpoint(TRUNCATE)
docker run --rm -v <project>_bridge-state:/state -v "$PWD/backup":/backup <любой-образ-с-cp> \
  sh -c 'cp -p /state/bridge.db* /backup/'
docker compose start bridge
```

Копируйте `bridge.db` вместе с `bridge.db-wal` и `bridge.db-shm`, если они есть: после аварийной остановки (SIGKILL) в `-wal` могут лежать подтверждённые транзакции, которых ещё нет в основном файле.

### Проверка копии

```bash
docker run --rm -v "$PWD/backup":/backup <образ-с-sqlite3> \
  sqlite3 /backup/bridge-<дата>.db "PRAGMA integrity_check; PRAGMA user_version;"
```

Ожидается `ok` и версия схемы (сейчас `1`, `SCHEMA_VERSION` в `src/store/sqlite.rs`).

## Restore

1. Остановить bridge: `docker compose stop bridge`. **Только при остановленном bridge.** Удалять `-wal`/`-shm` у работающей базы нельзя: подтверждённые транзакции из `-wal` будут потеряны.
2. В отдельном контейнере с тем же томом заменить `bridge.db` файлом из backup и удалить `bridge.db-wal` и `bridge.db-shm` (после `VACUUM INTO` они не нужны; копия самодостаточна). Права на файлы — пользователь `65532`.
3. Запустить: `docker compose up -d`. При старте выполнятся `integrity_check` и миграции; записи outbox в статусе `in_flight` вернутся в `pending`.
4. Убедиться: `docker compose ps` показывает `healthy`, в чате `/status` отвечает.

### Что происходит после отката к старой копии

1. Telegram может повторно прислать updates после сохранённого в копии offset (в пределах хранения у Telegram). Они обработаются как новые, но ответ в Paperclip не задублируется: повторный ответ получает `409`, bridge сверяет состояние карточки и закрывает запись как уже выполненную (`docs/ARCHITECTURE.md`, раздел 5).
2. Карточки, доставленные в Telegram **после** момента backup, bridge не знает; если они ещё pending в Paperclip, будут доставлены повторно новыми сообщениями. Старые сообщения в чате останутся «висеть» без обновления.
3. Ответы, поставленные в очередь после момента backup, но ещё не отправленные, теряются вместе с откатом; пользователь ответит на повторно доставленную карточку заново.

### Потеря состояния целиком

Bridge стартует «с нуля» на пустом томе: создаётся новая база, offset 0, и доставляются **все** карточки, которые сейчас есть в ленте `attention` (при более 10 новых — сначала сводка «Новых вопросов: N»). Уведомления о сбоях runs и завершённых задачах начинают с новой «нулевой точки» и старое не повторяют (`src/core/runs.rs`). Ответы не дублируются по той же причине, что и выше. `self_user_id` (идентификатор владельца ключа) bridge заново узнаёт из ответа Paperclip на первый успешный POST.

### Повреждённая база

Если при старте `integrity_check` не прошёл, bridge не запускается (в логе `bridge failed … state database failed the integrity check`). Автопочинки нет: восстановите из backup (выше) или, если backup нет, очистите том (это «потеря состояния целиком»).

## Периодичность

Рекомендация по умолчанию: ежедневный backup и перед каждым обновлением образа. Состояние небольшое, но оно содержит тексты карточек, поэтому ограничьте срок хранения копий.
