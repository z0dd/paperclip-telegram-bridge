# Backup и restore состояния

## Что в состоянии и что нет

Состояние — каталог `/state` (именованный том `bridge-state` в `deploy/compose.example.yml`): `bridge.db` с файлами `bridge.db-wal` и `bridge.db-shm`, а также `health.json` (его восстанавливать не нужно). В `bridge.db` (схема версии 2, [ARCHITECTURE](ARCHITECTURE.md) §3): offset Telegram, обнаруженные компании и беседы со связью «тема ↔ беседа» и курсорами комментариев, список уже виденных комментариев, очередь кусков ответов агентов для Telegram (`tg_outbox`) и очередь сообщений пользователя для Paperclip (`pc_outbox`). **Ключей Paperclip и токена бота там нет** (в базе только `key_ref`: номер ключа и короткий хеш); они лежат в файлах секретов, которые вы храните и копируете отдельно по своей политике. Но пока записи лежат в очередях, в базе есть тексты переписки с агентами, а постоянно хранятся названия компаний, имена агентов и идентификаторы бесед и тем: относитесь к копии как к конфиденциальным данным. Карточек v1 в базе нет: миграция 2 их удалила, сохранив только offset.

## Ограничения инструментов

- Runtime-образ distroless: нет shell, `sqlite3`, `tar`, `cp`. Внутри контейнера bridge ничего из перечисленного выполнить нельзя.
- Подкоманды `bridge backup` нет (ADR-0003). Online-копия делается **отдельным контейнером с `sqlite3`** над тем же томом; образ с `sqlite3` репозиторий не поставляет, возьмите любой подходящий.
- Команды этого документа в рамках этапа QA **не выполнялись** на реальном томе (нет Docker и развёртывания); они выведены из архитектуры (ADR-0003, раздел 3.3 архитектуры) и поведения SQLite. Перед тем как на них полагаться, проверьте backup и restore на тестовом томе.

Имя тома: `docker volume ls | grep bridge-state` (Compose добавляет префикс проекта). Ниже он обозначен `<project>_bridge-state`.

## Backup

### Вариант A: online, без остановки (рекомендуемый)

`VACUUM INTO` создаёт согласованную копию, не блокируя bridge надолго. Целевого файла не должно существовать.

```bash
mkdir -p backup
docker run --rm --user 65532:65532 \
  -v <project>_bridge-state:/state \
  -v "$PWD/backup":/backup \
  <образ-с-sqlite3> \
  sqlite3 /state/bridge.db "VACUUM INTO '/backup/bridge-$(date +%F).db'"
```

Том монтируется на запись, потому что SQLite в режиме WAL при чтении использует файл `-shm`; монтирование `:ro` может не сработать (не проверено). Каталог `backup` на хосте должен быть доступен на запись пользователю `65532` (или уберите `--user` и поправьте права получившегося файла).

### Вариант B: офлайн, с остановкой

```bash
docker compose stop bridge          # штатная остановка делает wal_checkpoint(TRUNCATE)
docker run --rm -v <project>_bridge-state:/state -v "$PWD/backup":/backup <любой-образ-с-cp> \
  sh -c 'cp -p /state/bridge.db* /backup/'
docker compose start bridge
```

Копируйте `bridge.db` вместе с `bridge.db-wal` и `bridge.db-shm`, если они есть: после аварийной остановки (SIGKILL) в `-wal` могут лежать подтверждённые транзакции, которых ещё нет в основном файле.

### Проверка копии

```bash
docker run --rm -v "$PWD/backup":/backup <образ-с-sqlite3> \
  sqlite3 /backup/bridge-<дата>.db "PRAGMA integrity_check; PRAGMA user_version;"
```

Ожидается `ok` и версия схемы (сейчас `2`, `SCHEMA_VERSION` в `src/store/sqlite.rs`). Копия, сделанная до обновления на v2, имеет версию `1` (карточки v1): при старте v2 её миграция удалит таблицы карточек и сохранит только offset.

## Restore

1. Остановить bridge: `docker compose stop bridge`. **Только при остановленном bridge.** Удалять `-wal`/`-shm` у работающей базы нельзя: подтверждённые транзакции из `-wal` будут потеряны.
2. В отдельном контейнере с тем же томом заменить `bridge.db` файлом из backup и удалить `bridge.db-wal` и `bridge.db-shm` (после `VACUUM INTO` они не нужны; копия самодостаточна). Права на файлы — пользователь `65532`.
3. Запустить: `docker compose up -d`. При старте выполнятся `integrity_check` и миграции; записи `pc_outbox` в статусе `in_flight` вернутся в `pending`.
4. Убедиться: `docker compose ps` показывает `healthy`, в логе нет ERROR, а сообщение в одной из тем доходит до беседы в Paperclip (команд в чате нет).

### Что происходит после отката к старой копии

1. Сообщения пользователя, которые bridge принял уже **после** момента backup, в копии отсутствуют. Если они успели уйти в Paperclip, комментарии там остались. Если не успели, они потеряны: подтверждённые Telegram updates Telegram повторно не присылает (по документации Bot API он забывает updates ниже подтверждённого offset), поэтому откат offset их не вернёт. Напишите такие сообщения заново. Если Telegram всё же пришлёт update повторно, дубля в Paperclip не будет: `clientRequestId` вычисляется детерминированно из `chat_id` и `message_id`, и Paperclip возвращает уже созданный комментарий без второго пробуждения агента ([ARCHITECTURE](ARCHITECTURE.md) §4.4 и §5).
2. Курсоры комментариев откатываются вместе с базой, поэтому ответы агентов, пришедшие после backup, прочитаются заново и **повторно** придут в темы (в Telegram это допустимый дубль, в Paperclip ничего не меняется).
3. Беседы, обнаруженные после backup, bridge не знает. Он обнаружит их заново как новые, создаст им **новые** темы и не будет пересылать историю до этого момента. Старые темы этих бесед останутся в группе без связи: сообщения в них получат подсказку «Эта тема не связана с беседой Paperclip», такие темы можно закрыть или удалить вручную. Темы, которые вы удалили в Telegram после backup, bridge создаст заново.
4. Сообщения пользователя, поставленные в очередь после backup, но ещё не отправленные, теряются вместе с откатом (см. п. 1).

### Потеря состояния целиком

Bridge стартует «с нуля» на пустом томе: создаётся новая база, offset 0. Компании и беседы обнаруживаются заново, **каждой беседе создаётся новая тема**, поэтому после потери состояния в группе остаются прежние темы без связи и их нужно убрать вручную; создание тем идёт через общую очередь (20 вызовов в минуту на группу). История бесед до повторного обнаружения в Telegram не пересылается: ответы агентов, пришедшие в период простоя, в темы не попадут, они остаются в Paperclip. Сообщения, написанные в старые темы, получат подсказку «Эта тема не связана с беседой Paperclip» и в Paperclip не уйдут. Дубли комментариев в Paperclip невозможны по той же причине, что выше (`clientRequestId`).

### Повреждённая база

Если при старте `integrity_check` не прошёл, bridge не запускается (в логе `bridge failed … state database failed the integrity check`). Автопочинки нет: восстановите из backup (выше) или, если backup нет, очистите том (это «потеря состояния целиком»).

## Периодичность

Рекомендация по умолчанию: ежедневный backup и перед каждым обновлением образа. Состояние небольшое, но оно может содержать тексты переписки из очередей, поэтому ограничьте срок хранения копий.
